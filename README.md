# Chefs Wheels · דף קביעת פגישות

דף יחיד שנשלח ללידים בקישור. הלקוח ממלא שם וטלפון, בוחר יום ושעה,
והפגישה נרשמת ישירות ביומן Google של העסק.

**ראשון–חמישי, 10:00–16:00, שישה תורים ביום.** אין מסד נתונים: היומן
הוא מקור האמת היחיד, ולכן אין שני מקומות שיכולים לצאת מסנכרון.

---

## הקמה חד-פעמית

### 1. הרשאת Google Calendar

אותו חשבון שירות שכבר משמש את מערכת הצעות המחיר יכול לשמש גם כאן.

1. ב-[Google Cloud Console](https://console.cloud.google.com/apis/library/calendar-json.googleapis.com),
   בפרויקט שבו נוצר חשבון השירות → **Enable** ל-Google Calendar API.
   בלי זה כל קריאה תיכשל ב-403.
2. פתח את [Google Calendar](https://calendar.google.com) עם החשבון של
   העסק → הגדרות היומן → **שיתוף עם אנשים ספציפיים** → הוסף את כתובת
   חשבון השירות (`...@....iam.gserviceaccount.com`) עם ההרשאה
   **"ביצוע שינויים באירועים"**.
   הרשאה נמוכה יותר תאפשר קריאה אבל לא רישום פגישות.
3. באותן הגדרות יומן → **התראות** → קבע התראת ברירת מחדל לאירועים
   (למשל דוא״ל שעה לפני). חשבון שירות אינו יכול לקבוע התראות עבור
   אדם אחר, ולכן זו ההגדרה שקובעת מתי תקבל תזכורת.

### 2. משתני סביבה

העתק `.env.example` ל-`.env` והשלם. המינימום: `GOOGLE_SERVICE_ACCOUNT_B64`
ו-`CALENDAR_ID`. מומלץ גם `BUSINESS_ADDRESS`, אחרת הדף לא יציג כתובת
וכפתורי ניווט.

### 3. הרצה ופריסה

```bash
npm install
npm run dev          # ממשק + הפונקציות האמיתיות, מול היומן
npm test             # בדיקות הלוגיקה (בלי רשת)
npm run build        # בדיקת טיפוסים מלאה + בנייה
```

`npm run dev` מריץ גם את הקוד שב-`api/` בתוך שרת הפיתוח (`dev/localApi.ts`),
ולכן הזרימה המלאה עובדת מקומית בלי חשבון Vercel. הפגישות נכתבות ליומן
האמיתי שב-`CALENDAR_ID`.

לעבודה על העיצוב בלי מפתח של גוגל ובלי לגעת ביומן, הוסף `MOCK_API=1`
ל-`.env`. אז נטען `dev/mockApi.ts` עם נתונים מומצאים. שני הפלאגינים
פעילים רק בשרת הפיתוח ואינם נכנסים לבנייה.

פריסה: חיבור ל-Vercel והגדרת אותם משתני סביבה תחת
Settings → Environment Variables.

### 4. אבחון פריסה

אם הדף מציג שגיאה, פתח:

```
https://<הדומיין>/api/health
```

הוא בודק את שרשרת ההגדרה לפי הסדר שבו היא נשברת — משתני סביבה, פענוח
המפתח, התחברות לגוגל, וגישה ליומן — ואומר איזה שלב נכשל ומה לעשות.
התשובה ציבורית ואינה מכילה שום ערך סודי.

> שינוי משתנה סביבה ב-Vercel **אינו** חל על פריסה קיימת. צריך לפרוס מחדש.

## שימוש יומיומי

### הקישור שנשלח ללידים

```
https://<הדומיין>/
```

אפשר למלא מראש את הפרטים שכבר ידועים, כדי שהלקוח רק יבחר מועד:

```
https://<הדומיין>/?name=ישראל%20ישראלי&phone=0501234567&ref=facebook
```

| פרמטר   | מה הוא עושה                                             |
| ------- | -------------------------------------------------------- |
| `name`  | ממלא מראש את שדה השם                                     |
| `phone` | ממלא מראש את שדה הטלפון                                   |
| `ref`   | מקור הליד. נשמר בתיאור האירוע ביומן, לא מוצג ללקוח        |

### לחסום זמן ביומן

כל אירוע רגיל ביומן חוסם את השעות שהוא תופס. בנוסף:

- **לסגור יום שלם** — צור **אירוע יומי** (כל היום) באותו יום, בכל שם
  שתרצה. אירוע יומי חוסם את היום גם אם גוגל מסמנת אותו כ"פנוי".
- **להשאיר שעה פנויה למרות אירוע** — סמן את האירוע כ**"פנוי"**
  (Free) בהגדרות האירוע. אירועים עם שעה שמסומנים כפנויים אינם חוסמים.
- ימי הולדת ומיקומי עבודה אינם חוסמים כלום.

### פגישה שנקבעה

האירוע נרשם בצבע צהוב ונושא את השם והטלפון בכותרת, ובתיאור יש קישור
וואטסאפ ישיר ללקוח, את ההערה שכתב, ואת מקור הליד.

**מחיקה של פגישה ביומן משחררת את השעה מיד.** אפשר גם להזיז פגישה לשעה
אחרת — השעה המקורית תתפנה לקביעה.

### ביטול מצד הלקוח

מסך האישור נותן ללקוח קישור אישי לביטול, שתקף **עד 24 שעות לפני**
הפגישה. מתחת לסף הזה הקישור מציג הודעה ומפנה לוואטסאפ — כדי שביטול
של הרגע האחרון יגיע אליך כהודעה ולא כשורה שנעלמה מהיומן.

## איך מובטח שלא יהיו שתי פגישות באותה שעה

בלי מסד נתונים אין נעילה, ולכן הנעילה נלקחת מגוגל עצמה.

לכל תור יש **מזהה אירוע דטרמיניסטי** שנגזר מהמועד:
`bk` + `YYYYMMDDHHMM` בשעון ירושלים + ספרת דור. שני לקוחות שלוחצים
"אישור" באותה שנייה מייצרים בדיוק את אותו מזהה, וגוגל מקבלת רק את
הראשון. השני מקבל 409 ורואה "המועד נתפס".

ספרת הדור קיימת כי מזהה שנמחק נשאר תפוס אצל גוגל לתמיד. כשמתקבל 409,
השרת בודק מה יושב על המזהה: פגישה פעילה שחופפת לשעה פירושה שהתור באמת
תפוס; פגישה שבוטלה או שהוזזה פירושה שרק השם תפוס, והשרת עובר לדור הבא.
בלי זה, מחיקה אחת של פגישה הייתה חוסמת את השעה הזו לצמיתות.

## מבנה

```
api/
  slots.ts     GET  → הימים והשעות הפנויים
  book.ts      POST → קביעת פגישה
  cancel.ts    GET/POST → פרטי פגישה / ביטול
  _lib/
    google.ts    JWT-bearer מול גוגל, בלי תלויות
    calendar.ts  עטיפה מעל Calendar API v3
    tz.ts        שעון ירושלים דרך Intl (מעברי שעון)
    slots.ts     חישוב התורים — פונקציה טהורה
    booking.ts   אירועים → זמנים תפוסים, ולולאת הדורות
    validate.ts  ולידציית הטופס בצד השרת
src/
  pages/       BookingPage (הטופס), CancelPage (ביטול)
  components/  שלבי הטופס ורכיבי UI
  lib/         קריאות לשרת, פורמט תאריכים, ICS
```

הלוגיקה המסוכנת — שעון, תורים, ולידציה, ומניעת הכפילות — מכוסה
ב-`api/_lib/*.test.ts` ורצה ב-`npm test` בלי יומן אמיתי.
